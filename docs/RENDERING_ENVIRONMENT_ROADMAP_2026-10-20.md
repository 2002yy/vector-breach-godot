# 角色、环境、投掷物与真实地图雷达：现状核对及实现方案

2026-10-20，按用户要求联网研究后续实现。核对基线 `16db93ea930fab5ee275031cf37a7f141dcaf20c`，分支 `fix/native-character-shading-20261020`。这是后续工程方案与缺口清单，未将建议写成已实现能力，也不改变上一候选包的验收结论。

## 推荐分批顺序

### P0：真实底图与投掷物规则

用户追加的真实击杀播报、队伍消息和友伤设置同属 P0，具体契约见下文。建议先收拢伤害/死亡事件，再扩展闪光/烟雾，以免重复维护多套规则；真实底图仍是下一批主要可见改进。

1. 小地图使用静态纹理底图和现有动态图标，避免再实时渲染一遍整张三维地图。优先定向提取本机原版 overview 及配置；当前已提取目录未见相关文件，不等同原 VPK 缺失。若来源/版本不对应，则从现有模型生成离线底图。
2. 无论采用哪种来源，保存 `world_to_map` 仿射变换、像素尺寸、地图/模型哈希和楼层高度区间。原版坐标需经过当前 Source→Godot 变换与偏移。以至少三个不共线锚点解算，再用其他路口复验，不能凭图像观感调比例。建议叠加误差小于玩家图标半径；遮挡信息仍沿用现有敌人发现规则，底图本身不暴露敌人。
3. 生成墙体/可走区/楼梯的清晰底图，处理屋顶遮蔽和多层重叠，按当前玩家或观战对象高度选层。真实俯视截图可作为参考层，不把屋顶覆盖当成可玩道路。
4. 恢复投掷物专用碰撞；记录已知高抛路线的发射点、初速、轨迹、天空接触和落点。开启连续碰撞/必要的扫掠查询前先验证现有刚体是否漏碰。修复手雷规则时不顺便改人物路网。
5. 闪光判定先统一到 actor 状态；AI 致盲期间的观察、报点与射击行为必须实际受影响。白屏、残像、音频包络与逻辑持续时间分别留证；既有 18 m/3.4 s 等数值是本作规则，未核验前不称作 CS 原值。

### P1：天空/环境光与可信烟雾

天空的 HDR 取值、色彩空间和反射强度需要一起核对。Godot `PanoramaSkyMaterial` 使用等距柱状全景，可接 HDR/EXR；原立方图需按正确面朝向转换。该接口适合保存原图动态范围，而不是把 LDR 背景强行提亮。[Godot 官方文档](https://docs.godotengine.org/en/stable/classes/class_panoramaskymaterial.html)

静态场景先评估离线 `LightmapGI` 和动态角色的 light probes，再增加少量室内 `ReflectionProbe`；优先静态/按需更新，避免每帧重捕获整图。先核验模型 UV2、拆分边界和探针覆盖，不直接对当前巨型地图盲目烘焙。Godot 确有动态对象光探针支持，但它不等于恢复 Source 的原烘焙数据。[LightmapGI](https://docs.godotengine.org/en/stable/classes/class_lightmapgi.html)、[ReflectionProbe](https://docs.godotengine.org/en/stable/classes/class_reflectionprobe.html)

烟雾建议先做墙体约束的粗密度网格：以投掷落点为种子，传播时查询真实碰撞；同一版本的密度快照供 CPU 视线积分和 GPU 采样。视觉可先试局部 FogVolume/自定义雾 Shader，再比较独立 raymarch 的代价。门口、薄墙、上下层、烟内及烟外必须验证：视觉不透而 AI 可见，或画面通透而判定完全遮挡，都不能通过。弹孔/爆炸排烟应作为后续玩法变更独立验证；不能因 Valve 展示过响应烟雾就声称这里已经具备。[Valve 官方烟雾说明视频](https://www.youtube.com/watch?v=_y9MpNcAitQ)

### P2：局部体积雾、专用角色效果及精修

Godot 的体积雾要求 Forward+；本机路径满足要求。先让全局体积密度为 0，少量局部 FogVolume 添加雾，控制有限雾距离与 froxel 分辨率。建议 32³/64³ 噪声纹理起步，通过真实镜头确认条带和拖影再调参数。短暂枪口灯/闪光的体积光能量宜为 0，以免时间重投影留下光迹。环境氛围雾与战术烟雾仍分开验收。[Godot 官方体积雾说明](https://docs.godotengine.org/en/stable/tutorials/3d/volumetric_fog.html)

角色效果继续使用固定版本的源码参考，而非猜测材质开关：

- 眼球：参考代码实际涉及眼遮罩、眼球球面求交、眼坐标、虹膜/瞳孔参数及颜色调整；先确认模型导出是否保留所需眼骨与位置数据，再接纹理，不能用额外白色高光代替。
- 逆反射：已有独立 `GetRetroReflectiveNormal`；核对原强度、纹理通道与运行时覆盖次序后移植，检查光源靠近/远离观察方向的区别。不能用发光材质替代。
- 发丝：先确认原切线、Alpha/裁切规则及 `F_ANISOTROPIC_HAIR` 的真实分支；已有 RG 各向异性粗糙度不自动代表发丝双高光等专用响应完成。
- 远距对比度：本轮仅确认源参数存在，尚未定位足够可靠的完整算法；仍标待研究，不臆造“随距离提亮”公式。
- 环境 BRDF、弯曲/软法线与骨骼空间：明确可取得的数据及近似项，固定同角色/同灯光/同曝光/同机位做参考对照；无原引擎金标准时保留等价性待核验。

参考：[固定 VRF 版本](https://github.com/ValveResourceFormat/ValveResourceFormat/tree/54279ec226cc3e1c561b10f11f0f5e879b981e6e/Renderer/Shaders)。这是查看器的公开重建实现，不是 Valve 官方完整着色器规范。本轮通过 GitHub API 实读 `csgo_character_eyes_ps.slang` 等文件，私有收据位于 `D:/AgentGamePipeline/evidence/rendering-roadmap-20261020/`；部分网页抓取失败不影响已下载源码，但未取得的算法继续开放。

## 逐项验收及性能

- 每个特效单独开/关，在同图、同路线、同分辨率与同版本下比较 CPU/GPU 帧耗、平均及低帧表现、显存与透明过绘；不能只看截图右上角的瞬时 FPS。
- 保持临时 2560×1600、平均 105 FPS 目标，当前仍未逐图最终验收；给特效分配预算前先重测最终候选基线。避免通过降低清晰度或关闭战术遮挡使性能“达标”。
- 三图连续试玩检查楼层雷达、投掷物穿墙/天空、闪光友军/敌军一致、烟内外 AI、死亡观战与换图清理；纯自动 UI 流程不算完整人工比赛。
- 本次仅研究和文档，无运行行为变化，因此不重复整套游戏测试。上一代码头的 Tests/Windows Export 全绿仍只证明该候选；未来实现改动需要重新执行对应测试、包和性能验证。

下一执行片：先补统一伤害/死亡事件、分离击杀与队伍消息并接友伤设置，再做三图真实地图雷达与坐标验收、闪光 AI 一致性及投掷物专用碰撞。若某张原 overview 与当前冻结地图变体不一致，则先生成对应离线底图，不通过更改碰撞/路网迎合图片。

## 追加：真实击杀播报、队伍消息、友伤及未来光追

### 已核对的实现

- `CombatHud.add_kill_feed` 已由 Main 的玩家/AI 射击、刀和燃烧伤害等入口调用，不能说完全没有真实播报。但当前只是 killer/victim/weapon 三字段文本，未集中到唯一死亡事件，也没有完整证明爆炸、自杀、友杀、穿透、爆头和助攻均正确。
- `show_radio_report` 与击杀条目共用 `KillFeed` 容器。CombatSandbox 已发送队友发现敌人/受击的事件；这是实际 AI 触发的无线电提示，尚不是独立队伍消息区，也不是玩家战术指令系统。
- `UserSettings` 无友伤持久化字段；玩家/AI 的通用伤害入口未看到统一的阵营过滤。关闭 AI 主动选择队友不能替代友伤策略。

### 实现契约与验收

1. **右上真实击杀流**：权威的角色存活→死亡转换发布一次带唯一 ID 的 DeathEvent，包含来源 actor ID/阵营、目标 ID/阵营、武器 ID、伤害种类、爆头/穿透、自杀/友杀和回合 ID。HUD 订阅结果，不由多个命中回调各自猜测。助攻必须从真实伤害账本计算，不能凭邻近队友补名字。爆炸/燃烧在投掷者死亡后继续保留归因；无攻击者的环境死亡有明确类型。
2. **展示**：右上紧凑条目、阵营颜色和武器图标，涉及自己的事件适度强调，限制条数与停留时间；核对金钱/FPS 占位，适配分辨率。切图、换边、回合重置不残留上局事件。检验一杀一条，死亡计数/计分板/经济归因一致，友杀不发正常击杀奖励。
3. **队伍消息**：无线电与击杀分区。只接本队实际观察、受击、C4 安装/掉落、投掷物与真实指令执行事件；带发送者和地区名、节流合并，禁止从隐藏敌方状态生成全知报点。后续“集合/守点/进攻 A/B/请求支援”等快捷命令需被 AI 真正消费并显示接收/执行状态；不能只回一条文字。
4. **友伤设置**：设置→对局规则中增加默认关闭、可持久化的友伤选项；开局复制为本场规则。局内更改建议下回合生效并明确提示，避免一次爆炸途中规则变化。统一 DamagePolicy 在扣血/扣甲前处理子弹、刀、爆炸、燃烧的来源与阵营。关闭时仍保留实体碰撞/挡枪，不默认允许子弹穿过队友；自伤、环境伤害与闪光致盲单独定义，不能随友伤开关误关。人工训练与竞技分别验证规则隔离。
5. **对称回归**：玩家→队友、AI→玩家、AI→AI 各伤害类型，开关两态；延迟爆炸/持续火、投掷者死亡、换边后旧来源、友军护甲不变、死亡只记一次及友杀经济都需覆盖。默认关闭是新增产品规则，不宣称当前已经禁止友伤。

### 未来光追：具备底层起点，尚无即用开关

联网核验确认 Godot 的 Vulkan 光追底层合入 PR [#99119](https://github.com/godotengine/godot/pull/99119) 于 2026-01-27 合并。不能沿用“Godot 完全没有光追”的旧说法；同样不能把 SSR/SDFGI 命名成硬件光追。[官方引擎讨论](https://github.com/godotengine/godot-proposals/discussions/5162)、[渲染功能表](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)

本机 4.7.1 ClassDB 实查有 `blas_create/build`、`tlas_create/build`、`raytracing_pipeline_create` 等方法和 `SUPPORTS_RAYTRACING_PIPELINE`。Forward+/Vulkan 的本地 RenderingDevice 查询返回支持。收据：`raytracing-capabilities.json` 与 `raytracing-device.json`。这只证明接口和设备特征可用，未构建场景 BLAS/TLAS，也未完成任何光追画面或性能验证。

建议先独立原型验证静态场景 RTAO 或小范围 RT 阴影，再决定是否提供实验选项。RT 反射/GI 另评估材质访问、透明/Alpha 裁切、蒙皮更新、动态物体、降噪和历史缓冲重置；不能假定底层接口会自动继承当前 Godot/Source 材质。设置仅在效果实现且设备/驱动可用后显示，默认关闭；无支持时给原因并回退现有渲染。每项按实际效果命名（如“光追阴影·实验”），避免只有笼统“RTX 开启”按钮。功能必须接受同一帧率目标下的实测取舍，未来路线不阻塞当前竞技基础功能。
